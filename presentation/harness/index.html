[1:20-2:05 | Slide 3. Point to the fixed workflow first, then the policy chain.] A fixed workflow is a good baseline for this example. An agent could choose its next request based on an unexpected result or missing evidence. The model can choose requests, but Python controls execution. The gateway requires context before balance, then a source check. Those releases cost one, two and two units, within a five-unit allowance per site and case. Repeating a released product uses the cache. These are disclosure accounting units. They don't provide differential privacy, and we haven't yet measured whether the agent makes better decisions than a fixed workflow.

[2:05-3:25 | Slide 4. Trace the loop, then point to the two state stores.] Here is where Flower comes in. It loads our AgentApp and calls its Python entry point. Our application sends the question and tool definitions to Flower's model endpoint. The model returns a structured tool request. Our code checks the arguments and dispatches it. For a facility evidence request, a separate steward model context can ask for release or decline. Even if it asks for release, the gateway still applies its rules. The result goes back into the investigator's context, and the model can choose another request. We bound that loop; the defaults are eight planning turns and sixteen tool calls. Then we request a final report with tool use disabled and publish its streamed events through Flower. Flower supplies execution, model access, events and run-series state. We wrote the loop, tools, stewards and disclosure policy. Our app uses custom site adapters. Flower holds the run-series state; the gateway uses a separate SQLite ledger. The default sites share one process. Separate site services are supported; this example runs locally.
