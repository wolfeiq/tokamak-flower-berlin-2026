FIVE-MINUTE HARNESS SEGMENT
Six slides within the team's twenty-minute presentation. Aim for 125-130 words

1. What it is, and who it is for

[0:00-0:40 | Slide 1. Begin after the broader project's introduction.]

I'll focus on the investigation assistant we built with Flower's agent harness.

Imagine a plasma is colder than expected after heating. Did more heat escape, or did less power actually reach it? What evidence would separate those explanations?

Fusion Investigator helps with that work between experiments. It asks configured tools for evidence and recommends a measurement. It's for physicists and diagnostic teams. The harness is the software around the model that runs the investigation.

2. What goes in, and what comes out

[0:40-1:20 | Slide 2. Follow the three columns from left to right.]

The input is a research question and a set of configured sites. Site analysis uses temperature, density and heating profiles. Our example uses synthetic data from a reduced transport model.

The investigator receives specific products: machine context, a transport category, a rounded profile, or a source-audit result. It can also receive a refusal.

The intended output is a report citing that evidence, explaining what's still unknown, and recommending the next measurement. We keep the tool results alongside it so researchers can check its claims.

3. Why use an agent here?

[1:20-2:05 | Slide 3. Point to the fixed workflow first, then the policy chain.]

A fixed workflow is a good baseline for this example. An agent could choose its next request based on an unexpected result or missing evidence.

The model can choose requests, but Python controls execution. The gateway requires context before balance, then a source check. Those releases cost one, two and two units, within a five-unit allowance per site and case. Repeating a released product uses the cache.

These are disclosure accounting units. They don't provide differential privacy, and we haven't yet measured whether the agent makes better decisions than a fixed workflow.

4. What Flower does during a run

[2:05-3:25 | Slide 4. Trace the loop, then point to the two state stores.]

Here is where Flower comes in. It loads our AgentApp and calls its Python entry point. Our application sends the question and tool definitions to Flower's model endpoint.

The model returns a structured tool request. Our code checks the arguments and dispatches it. For a facility evidence request, a separate steward model context can ask for release or decline. Even if it asks for release, the gateway still applies its rules.

The result goes back into the investigator's context, and the model can choose another request. We bound that loop; the defaults are eight planning turns and sixteen tool calls. Then we request a final report with tool use disabled and publish its streamed events through Flower.

Flower supplies execution, model access, events and run-series state. We wrote the loop, tools, stewards and disclosure policy. Our app uses custom site adapters.

Flower holds the run-series state; the gateway uses a separate SQLite ledger. The default sites share one process. Separate site services are supported; this example runs locally.

5. The heating example

[3:25-4:25 | Slide 5. Read A, B, C, then follow the arrow to the recommendation.
This is a static summary of captured gateway outputs, not a live agent run.
Keep the optional replay closed during the five-minute talk.]

This example shows the kind of evidence the loop can receive. These are actual gateway outputs from three synthetic facilities; no model chose this sequence.

At A, transport appears elevated, but that calculation assumes the commanded heating was delivered. A has no independent source audit, so the cause stays open.

B has an audit in this constructed scenario. It reports lower delivered power. Recomputing transport with that source brings it near the reference. That suggests a useful measurement at A; it doesn't diagnose A.

C fails the demo's gradient criterion, so the gateway refuses its balance result. That is a chosen applicability rule, not a universal statement about plasma physics.

The recommendation is to independently verify delivered heating at A.

6. What we can claim, and what comes next

[4:25-5:00 | Slide 6. Finish with the evaluation, then hand back to the team.]

We have an executable investigation workflow with controlled evidence requests and a record we can inspect.

The next evaluation is an agent against a fixed workflow, with the same tools and budgets, on cases it hasn't seen. We'd measure whether it recommends a useful diagnostic, respects the limits, and how much time and model use it costs.

For this example, the useful outcome is knowing what to measure next, while leaving A's diagnosis open.
